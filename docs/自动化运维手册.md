# 自动化运维手册（给以后接手跑的 AI 看）

> 用途：这个项目最终要由 AI 自动运行。这份文档把「我已经踩过的坑 + 现象 + 判断依据 + 处理办法」写下来，
> 遇到问题先查这里，不要重新试错。
> 更新：2026-11-17

## 0. 每次开工前的 30 秒自检

```bash
python tools/x_probe.py --status          # 端口/登录/页面
python tools/x_health.py                  # 账号体检（档位、额度、受限提示、行为设置）
python tools/x_isolation_check.py         # 依赖是否走 vendor，不依赖外部仓库
```

必须确认三件事：
1. **档位对不对**：`test`=9234（小号，可随便试）/ `prod`=9235（正式号）。看 `config.instance_banner()`。
2. **账号闸门过不过**：窗口登录号必须等于 `xauto/data/accounts.json` 里该档位的值，否则工具会直接退出（设计如此）。
3. **窗口在屏幕内**：`window.screenX` 如果接近 `-32000`，说明被"停车"到屏幕外，真实鼠标点不到 → 调 `input.bring_window_on_screen()`。

## 1. 已知故障清单（现象 → 原因 → 处理）

### 1.1 点击没反应 / 鼠标一直偏移
| 项 | 内容 |
|---|---|
| 现象 | 日志显示点击成功，但页面没变化；或日志里反复出现「坐标已标定」且偏移量每次不同 |
| 根因 A | **窗口不在屏幕内**（x=-32000）。真实鼠标移不到那里 |
| 根因 B | **多个浏览器窗口**：双档位时两个 Edge 标题一样，`focus_window` 会提到错的窗口 |
| 根因 C | 上一版把每次局部修正**累加**进偏移缓存 → 越点越偏 |
| 处理 | ① `input.bring_window_on_screen(title)`；② `ensure_foreground` 已改为「以 OS 前台窗口为准 + Page.bringToFront」；③ 标定改为**绝对保存、不累加**，且只用「页面上唯一的锚点」 |
| 自检 | `xi.calibrate_window(cdp, force=True)` 应打印 `ox/oy` 且两个锚点一致；随后 `screen_point` + `_hover_leaf` 应命中目标 testid |

### 1.2 标定失败：`标定结果不一致` 或 `锚点都没命中`
| 项 | 内容 |
|---|---|
| 根因 | ① 用 href 选择器时页面有多个同名链接（顶栏 + 左栏），扫描命中了另一个；② 目标元素尺寸为 0（被折叠） |
| 处理 | 只用 `document.querySelectorAll(sel).length === 1` 的唯一锚点（当前用 `AppTabBar_Home_Link` / `AppTabBar_Explore_Link`）；不一致时丢弃第二组、只信第一组 |
| 注意 | 详情页/窄窗口下左栏可能收起，`AppTabBar_*` 可能不存在 → 兜底锚点用 `SideNav_NewTweet_Button` |

### 1.2a 标定偏移 20px：小元素（作者名）点空
| 项 | 内容 |
|---|---|
| 现象 | 大按钮（导航）点得中，小链接（`User-Name` 约 20px 高）坐标对但悬停链里没有它 |
| 根因 | 标定扫描把「命中区间的**上边缘**」当成了元素中心 → ox/oy 系统性偏 ~20px；大元素容错高看不出来，小元素直接偏出 |
| 处理 | `_scan_axis` 找完整命中区间取**中点**（2026-11-17 已修）；验证法：`elementFromPoint` 与真实悬停链交叉比对 |

### 1.2b 坐标偏 1200px：目标在视口外时点击
| 项 | 内容 |
|---|---|
| 现象 | 日志「坐标未命中 …放弃这次点击」；移动前读到的矩形 y=-984（视口外） |
| 根因 | 目标在视口外/边缘时，鼠标移过去会触发 X 时间线自动滚动，读到的坐标是**滚动中的过渡值** |
| 处理 | `click_expr` 点击前先 `scroll_into_view()`（滚到视口中部 + 连续两次矩形一致才算稳定）；重标定后同样要再滚一次 |

### 1.3 输入框「读回为空」/ 打不上字
| 项 | 内容 |
|---|---|
| 现象 | `fill_editor` 后读回 `''`，或 `回复框内容与预期不一致` |
| 根因 | 真实鼠标模式下只调 `el.focus()` 不够，页面焦点会被自己抢走；或点击编辑器失败 |
| 处理 | `fill_editor` 现在**先真实点击编辑器**再输入；输入改为逐字符 `WM_CHAR`（含中文），间隔 `behavior.typing_ms`（默认 130ms） |

### 1.4 提交后「没有成功证据」
| 项 | 内容 |
|---|---|
| 现象 | `两次点击都没有成功证据`，但内容其实已经发出去了 |
| 根因 | 判据太窄：只认 toast + 编辑器清空。X 有时既不弹 toast 也不清空编辑器（实测能查到已发出的内容） |
| 处理 | 判据加了第三条、也是最强的一条：**页面 innerText 里出现我们刚写的正文前 24 字** → 视为成功 |
| 额外兜底 | 点按钮无证据时，自动改用 **Ctrl+Enter**（X 原生快捷键）再试一次 |

### 1.5 通知匹配不到「别人回复我」
| 项 | 内容 |
|---|---|
| 根因 | X 中文通知有两种写法：`回复了你` / `回复 @你的handle`；早期只匹配了前者 |
| 处理 | `read_notifications(me=handle)` 同时匹配两种（大小写不敏感）；调用方必须传 `me` |

### 1.6 帖子不可用还去回复
| 项 | 内容 |
|---|---|
| 处理 | 打开详情后先调 `p.post_available()`；命中「此帖子不可用 / This post is unavailable / 帖子已被删除…」或既无正文也无编辑器 → 跳过，不计失败 |

### 1.7 发帖页/草稿挡住导航
| 项 | 内容 |
|---|---|
| 现象 | 停在 `/compose/post`，点左栏没反应，`goto_notifications` 失败 |
| 处理 | `p.discard_drafts()`：清空编辑框 → 点关闭 → 若弹「保存草稿？」选**不保存**；`ensure_home()` / `goto_notifications()` 会先调它 |

### 1.8 评论生成被判不合格（SOP 校验）
| 项 | 内容 |
|---|---|
| 现象 | `两版都没通过 SOP 校验：没有接住原帖的具体点` |
| 说明 | **这是设计行为**，不是 bug。纯图/GIF/极短帖本来就没有可接的具体点 |
| 处理 | 跳过即可，不要为了凑数放宽校验 |

### 1.9 插件版：反复点同一处空点（落点没校验）
| 项 | 内容 |
|---|---|
| 现象 | 插件版（extension/）操作时，鼠标反复移向同一个位置、点了又退回、再点，页面毫无反应 |
| 根因 | 第一版 content.js 把 `getBoundingClientRect` 的 CSS 坐标**直接**喂给 CDP `Input.dispatchMouseEvent`，中间没有任何校验。CDP 落点与 CSS 坐标在页面缩放、时间线自动滚动、窗口状态变化时会系统性偏差 → 每次点的都是空气；`clickEl` 返回的 `res.ok` 只说明「事件发出去了」，不代表点中了 |
| 处理 | 现在每次点击前：移过去 → 检查目标元素 `el.matches(":hover")` → 不中就按由近及远扫描修正（±24px，步长 8px）并累计全局偏移；会话开始先用导航锚点标定一次。扫不到就**跳过这次点击**并记日志，绝不空点 |
| 边界 | 标签页不可见时 `:hover` 可能永远不亮：连续 3 次失败自动退回「直点模式」，日志会写明。**要让校验全程有效，x.com 标签页保持可见**（窗口不必前台） |
| 自检 | 控制台活动日志出现「落点已标定：偏移 dx=.. dy=..」= 标定生效；出现「落点校验失败」= 该元素确实点不到，跳过是正确行为 |

### 1.10 插件版：操作太快像机器人
| 项 | 内容 |
|---|---|
| 现象 | 用户观感：移动/点击/停顿节奏偏快，机器感强 |
| 处理 | 全局速度系数 `speed`（面板「速度系数」，默认 1.5=慢一半）作用于移动步间、悬停、按压、滚动间隔、扫读/阅读停顿、写操作间隔；打字速度独立（`typing_ms`，默认 130，别乘系数——那是硬约束） |
| 别动 | 提交后的证据轮询间隔**不**乘系数：那是等服务器响应，不是人的节奏 |

### 1.11 插件版：慢网上页面还没加载完就点/就退
| 项 | 内容 |
|---|---|
| 现象 | 用户网速慢：页面还在转圈，程序已经完成点击并离开——打在旧 DOM 上，等于白点 |
| 根因 | 第一版只靠固定 settle 等待，慢网下不够；SPA 换页/切栏目/滚动分页都是分批渲染 |
| 处理 | 所有导航后加三重等待：① 转圈消失（`[role="progressbar"]:not([aria-valuenow])`，后者排除视频音量条）② 帖子数量连续两轮询稳定 ③ 内容签名（条数+首条文本）真的变化。滚动后等新帖追加；连续 3 次滚动无新帖=到头，滑回顶部等下轮。超时不死等，写日志后按当前状态继续 |
| 自检 | 日志出现「加载较慢，继续等待渲染…」= 监控在工作；频繁出现考虑调大 speed 或检查网络 |

### 1.12 插件版：点赞到底点没点上（状态验证）
| 项 | 内容 |
|---|---|
| 现象 | `clickEl` 返回 true 只代表事件发出去了，不代表按钮状态翻转；留档写 like:true 但实际没赞上 |
| 处理 | 点赞后必须验证 `[data-testid="like"]` → `[data-testid="unlike"]` 翻转（6s 内），关注验证 follow→unfollow；没翻转记 ✗ 且留档如实记「想赞但没点到」 |
| 意义 | 统计和留档只记真实发生的动作，额度才不会被幽灵点赞吃掉 |

### 1.13 插件版：「注入页面」按钮要点个不停（2026-11-18 已根治）
| 项 | 内容 |
|---|---|
| 现象 | 用户每换一页/往下多看几屏就想点一次「注入页面」，问是不是只能注入当前页面 |
| 根因 | `chrome.scripting.executeScript` 确实只注入**指定 tab 当前文档**一次；但页面内滚动、点进帖子是 SPA 换页不换文档，脚本一直驻留，本不需要重注。真正要重注的场景是：**扩展重载/更新后，已开着的 x.com 标签页里旧脚本上下文失效**（chrome.runtime 断开，消息发不出去） |
| 处理 | 三层自动兜底（幂等，content.js 有 `__XA_LOADED__` 守卫）：① manifest `content_scripts` 页面加载自动注入；② background 监听 `tabs.onUpdated`(status=complete) 对 x.com 补注入；③ `onInstalled`/`onStartup` 把所有已开 x.com 标签页补注入。控制台渲染时 ping 失败也自动补注入一次，UI 文案不再引导手点 |
| 自检 | 重载扩展 → 已开着的 x.com 标签页**不刷新** → 控制台应直接显示可启动/运行中；若出现「页面未注入」检查 background 是否抛错（`chrome://extensions` → Service Worker → console） |
| 边界 | `chrome://` 等非 x.com 页注入会静默失败，属正常；服务 worker 冷启动到 onInstalled 有毫秒级延迟，极端慢网下首次注入可能晚于页面首屏，等下一轮 onUpdated 兜底 |

### 1.14 插件版：时间线无限流 / 滑到旧帖 / 加载停滞（2026-11-18）
| 项 | 内容 |
|---|---|
| 现象 | X 时间线新帖在上方，一直往下滑会滑到以前的帖子；有时滚动了但页面不出新帖（加载停滞） |
| 处理 | ① 滚动后 `waitMoreArticles` 最多等 20 秒（慢网分页请求晚到是常态）；② 连续两轮没有新帖 → `refreshOrTop()`：优先点顶部蓝色「新帖」箭头（`[aria-label="New posts"]` 等选择器）回顶并触发刷新，没有该按钮就滚轮回顶；③ 回顶后仍无变化 → 停 8~15 秒再继续，不死循环 |
| 判定 | 日志「连续滚动都是读过的帖子（滑到旧帖区或加载停滞）→ 回顶部找新帖」= 触发；「点顶部「新帖」箭头回顶刷新」= 蓝箭头路径生效；「滚回时间线顶部等新帖」= 无箭头退化路径 |
| 注意 | 蓝箭头只在有新帖且用户已下滚时出现；没出现属正常，退化到滚轮回顶即可 |

### 1.15 插件版：评论规则双模式 / 中文被判成「纯符号」（2026-11-18）
| 项 | 内容 |
|---|---|
| 背景 | 用户要求：「原有规则保留，现在加上我的规则，并且现在使用我的规则」——我的规则：什么帖子都能评论、≤20 字、13 字左右随机、内容 = 回应帖子 + 表达观点 |
| 实现 | `sop.js` 的 `isMineMode(beh)`（`beh.comment_rule`，默认 `"mine"`）分流：`shouldSkip`/`shouldComment`/`validateComment` 都按模式走；`comment.js` 的 `generateMine()` 专门出短评（LLM 极简指令 + 12 条短句模板，`{p}` 填原帖短语）。原 SOP 分支一行未删 |
| 字数 | `SOP.commentLength(beh)` 返回 `{lo, hi, cap}`：cap 硬顶 20，目标 `comment_target_len`（默认 13）±5 随机，每次生成独立摇一次 |
| 坑（已修） | `/^[\s\W_]+$/` 在 JS 里把**中文也算 `\W`**，导致所有中文评论被判「纯表情/纯符号」而全部失败。改用 `/^[\s\p{P}\p{S}\p{Emoji_Presentation}]+$/u`（`PURE_SYMBOL`）。**以后写字符类正则一律用 `\p{...}` + `u` 标志** |
| 坑（已修） | 我的规则最初仍被 `shouldSkip` 里「正文过短且无可读信息」拦住，短帖通过率 0%。现在该条只在 SOP 模式下生效；垃圾词（互关/抽奖/广告）两套模式都跳 |
| 自检 | 离线跑：短帖/正常帖评论通过率均应 ≈ 评论概率（默认 85%）；超 20 字必须被拒；「说得很好学习了」在我的规则下通过、SOP 规则下拒绝 |
| 面板 | 控制台新增「SOP 判定参数（高级）」栏：评论规则、目标字数、评论去重、点赞/评论概率上限、展开字数门槛、写操作间隔上下限、重点关键词。侧边栏同步评论规则与目标字数 |

### 1.16 插件版：控制台排版 / 统计下钻 / 日志分色（2026-11-18）

### 1.17 插件版：API Key 每次要重填 / 评论参数分散（2026-11-18）
| 项 | 内容 |
|---|---|
| 现象 | 用户反馈「api 这种隐私信息到设置里面填写，然后保存本地，不要每次都重新填」 |
| 根因一 | `dashboard.js` 的 `saveSettings()` 只把**当前页面存在的**字段放进对象，然后 `chrome.storage.local.set({xa_settings: s})` **整体替换**。侧边栏（panel.js）和控制台（dashboard.js）的 FIELDS 列表不同，两边各自保存就会抹掉对方的字段 → Key 丢失 |
| 根因二 | 侧边栏 load 时把已存的 Key 填进输入框，但如果用户没动它、某些路径下取到空值，保存就写回空串 |
| 处理 | ① 两处 `saveSettings` 全部改成**读旧值 + 展开合并**再写；② `llm_key` 留空时 **`continue` 跳过**（空 = 保持原值），要清除必须显式点「清除 Key」；③ API 配置抽到独立键 `xa_llm`（`{apiKey, baseUrl, model}`），`content.js` 的 `getBeh()` 读 `xa_llm` 优先、回退旧 `xa_settings.llm_*` 完成迁移 |
| 自检 | 填 Key → 保存 → 关窗口 → 重开控制台，Key 应自动带出且显示为 `abcd…wxyz` 掩码；再点一次「保存设置」（不碰 Key 输入框）后重开，Key 仍在 |
| 评论参数窗口 | 新增 `comment-rule.html/js`：规则切换、触发条件、字数、语气、**提示词全文**、**模板句全文**、实时预览一页搞定，存回 `xa_settings`（提示词/模板与其它设置同键，`getBeh` 直接读到）。`comment.js` 暴露 `DEFAULT_MINE_PROMPT` / `DEFAULT_MINE_TEMPLATES`，值等于默认时**不落库**，以后改默认能自动跟上 |
| 字数坑（已修） | 模板兜底原先用 `shortPhrase(post, len-6)` 截短语，没算模板自身字数 → 长模板撞 20 字上限被判不合格、评论直接发不出去。现按 `fixed = tpl.replace("{p}","").length` 反推短语可用长度，并用 `tryTemplates()` 换模板重试。实测目标 13 字：0 失败 / 100 次，范围 8~18，均值 13.5，0 条超 20 字 |

### 1.18 插件版：自己给自己回复 / 没帖子不回顶 / Show N posts（2026-11-18）
| 项 | 内容 |
|---|---|
| 现象 | 用户看日志发现：**同一个帖子（自己的回复）被连续回了 3~4 条**；没帖子时不会点「Show 105 posts」；刷新过于频繁，反复刷同几条 |
| 根因一 | `whoami()` 早就写了，但**只在关注流程里用过**，选帖 `stepHome` 完全没调用 → 自己的帖子和自己发的回复照常被选中、点开、评论。一个号自己跟自己对话，是平台判定刷量最硬的证据 |
| 处理一 | 选帖时 `handle.toLowerCase() === whoami().toLowerCase()` 的全部排除；整屏都是自己的就往下翻，连续 4 屏仍如此则 `refreshOrTop()`。**三条路径各自兜底**：`stepDetail` / `stepNotifReply` / `stepProfile` 进来后都复查一次。`whoami()` 返回空时写 `⚠` 日志告警，**绝不静默失效** |
| 根因二 | `refreshOrTop()` 只找 `[aria-label="New posts"]` 等固定选择器，没覆盖时间线顶部那颗 **「Show 105 posts」** 文字按钮（X 改版后常见形态） |
| 处理二 | 遍历 `button` / `div[role=button]`，按**可见文案**匹配 `/Show\s+\d+\s+posts?|显示\s*\d+\s*条|\d+\s*posts?|新帖子|new\s+posts?/i`，且要求 `getBoundingClientRect()` 宽高 > 0（可见）。找到就点，日志记「点「Show 105 posts」拉新帖」。固定选择器保留作第二优先级 |
| 根因三 | 刷新门槛太低，读一两条就回顶 → 反复刷同一批帖子 |
| 处理三 | 新增参数 `min_read_before_refresh`（面板「刷新前至少读」，默认 **12** 篇）。本轮 `homeReads < 12` 时只往下翻不刷新，日志写「本轮才读 X/12 篇 —— 继续往下翻，先不刷新」；真刷新后 `homeReads` 归零重新计 |
| 自检 | 小号跑一轮：日志里不应出现「✓ 评论 @<自己的号>」；「读到自己帖子」的行应显示「跳过」；刷新区应出现「点「Show N posts」拉新帖」而不是「滚回顶部」 |

### 1.19 插件版：烂评论 / 重复评论 / 开始不刷新 / 发现页语义（2026-11-18）
| 项 | 内容 |
|---|---|
| 现象一 | 用户看到「✓ 主页互动：评论 @xxx：`5、开源免…，短期热闹长期未必。`」——`{p}` 被填成数字开头的残句 |
| 根因一 | `shortPhrase()` 只做「挑最长子句 + `cut()` 硬截」，且 `cut()` 末尾会补 `…`。于是列表型帖子（`1、开源免费真香，5、开源免…`）被抓出半截编号句，再拼模板 = 机器味极重 |
| 处理一 | 四道过滤：① `/^[\d\s.、,，)）]/` 开头直接丢；② **含 `…`/`...` 的残句直接丢**；③ `FILLER` 全虚词校验；④ `usablePhrase()` 去掉虚词后仍需 ≥4 实字。`shortPhrase()` 只在 ①整句合适 ②逗号分段合适 时返回，**否则返回空**；`mineTemplate()` 拿到 null 就换模板，全都不行则退回 `NO_PHRASE_TEMPLATES`（不带 `{p}` 的纯观点句）。实测 50 条：省略号残留 0、空结果 0、字数 11~19 |
| 现象二 | 重复评论，尤其在别人主页：同一个作者的多条帖子被回了一模一样的话 |
| 根因二 | 只有「同帖 ID 去重」，**没有跨帖去重**；LLM 每次都是全新上下文，不知道以前说过什么 |
| 处理二 | 三层：① 同帖 ID（原有）；② `withAntiRepeat(post)` 把**同作者历史评论**塞进 `post.myReplies`，提示词明写「绝对不要再说一遍」；③ 全局 100 条历史用**字符二元组相似度**（bigram，对中文短句比编辑距离稳）≥0.6 判重复，LLM 换角度重写、模板换下一条。`noteComment()` 在详情页/主页/通知三处评论成功后立即入历史 |
| 现象三 | 任务开始不刷新，拿到的是旧时间线 |
| 处理三 | `startSession()` 先调 `hardRefreshTimeline()`：优先点「Show N posts」/「新帖」，否则滚顶后点首页 tab 触发重载 |
| 现象四 | `explore_prob` 语义被误解成「跳过概率」 |
| 处理四 | 用户明确：这是**未关注用户中点进主页浏览的比例**。没命中的改为**就地关注**（该行 Follow 按钮，`followStateIn` 同款翻转校验），命中才进主页走「翻 10 条 + 互动 3~5 篇 + 关注」。两者都受 `max_follow` 约束 |
| 现象五 | 会话统计不实时 |
| 处理五 | `startStatsSync()` 每 1.5s 写 stats/phase/now 快照；`stopSession()` 清理。注意 `statsTimer` 用 `let` 提前声明避免 TDZ |
| 评论提示词 | 对齐用户给的 `CommentPrompts.kt`：system 要求「① 对内容有具体回应，不能是空话；② 表达自己观点，不要复述原文」，并加「不要编造数据/亲历、不评价作者本人」；user 侧传 `作者 / 主内容 / 已有回复（不要重复）/ 我之前发过的（换个角度）/ 请给出 1 条 N 字评论` |

### 1.20 插件版：通知页三类分流 + 关注限流（2026-11-18）
| 项 | 内容 |
|---|---|
| 背景 | 用户给出通知页截图，明确三类：① 别人回复我的帖子 → 点进去回；② 别人关注我 → 点进去看主页再关注；③ 别人点赞我的帖子 → 不管。并要求「关注要有时间限制，短时间不能关注太多人」 |
| 通知分类 | `readNotifications()` 重写，按文案分 kind：`follow`（`followed you|关注了你`）、`like`（`liked your post|喜欢了你的`）、`reply`（`repl(i|y)(ing|ed)?\s*to|回复了|mentioned you`）。**顺序很重要**：先判 follow，再 like，最后 reply —— 否则「X followed you」被 reply 正则误吞。自己触发的通知（handle === 我）跳过 |
| 回复上下文 | **关键坑**：通知里点进去，页面第一条通常是**对方的回复**，我的原帖在下面。旧代码 `readTweets(3)[0]` 拿到的是他的话，却被当作「帖子」喂给生成器，等于在回复里再复述他的话。现在 `readTweets(6)` 里分别找 `isMyHandle()` 的那条（= 我的原帖）和别人的那条（= 他的回复），作为 `ctxMyPost` / `ctxReply` 传给 `COMMENT_GEN`，提示词据此走「对话式回应」分支 |
| 新粉丝 | `stepNotif` 里 follow 类改为点**用户名链接**进主页（不是点帖子），复用 `stepProfile` 的「翻 10 条 + 互动 3~5 篇 + 关注」 |
| 关注限流 | `followAllowed(beh)` 三道闸：① 距上次关注 ≥ `follow_gap_min~follow_gap_max`（默认 60~180 秒，每次随机目标值）；② 本小时 < `follow_per_hour`（默认 8）；③ 今日 < `max_follow`（默认 25）。另有 `follow_per_session`（默认 5）限制单轮。**所有关注路径**统一走 `noteFollow()` 记账，避免某条路径绕过 |
| 自检 | 日志应出现「通知：N 条 · 待回复 X · 待看新粉丝 Y · 点赞类 Z 条（忽略）」；关注被拦时写「暂不关注 @xxx：距上次关注才 N 秒」或「本小时已关注 N/8」 |

### 1.21 插件版：通知回关整条链路没跑（2026-11-18）
| 项 | 内容 |
|---|---|
| 现象 | 用户反馈「通知回关这个步骤没有执行」，期望：点头像 → 进主页 → 浏览帖子 → 点赞关注 |
| 根因① | **`notif_enabled` 默认 `false`** —— `startSession()` 里 `phase: beh.notif_enabled ? "notif" : "home"`，通知阶段压根没进入过。已改为默认 **true** |
| 根因② | 通知是**虚拟列表**，一屏只渲染 5~6 条，新粉丝常在下面。旧代码进页面直接 `readNotifications()`，底部的新粉丝读不到。新增 `scrollNotificationsToLoad()`：滚到底加载、连续两次无新增即停、滚回顶部再收集（`readNotifications` 上限提到 40） |
| 根因③ | 聚合卡片「加密老熊 and 5 others followed you」里有**多个头像**，旧代码取 `SEL.userNameLink` 第一个 → 会点进别人主页、关注错人。现在按 `handle` **精确匹配**卡片里的链接再点，点完还用 `location.pathname` **校验真的到了他的主页**，不对就退回通知页 |
| 根因④ | `stepProfile` 结尾无条件 `goHome()`，从通知页进来处理完一条就回首页，后面的新粉丝再也轮不到。新增 `ctx.fromNotif` 标记，处理完回**通知页**继续下一条 |
| 根因⑤ | 回复类和关注类共用同一个 20% 时间配额，回复一多就把时间吃光。现在分开：回复类 20%、关注类 40% |
| 自检 | 日志应依次出现「通知：N 条 · 待回复 X · 待看新粉丝 Y」「新粉丝 @xxx → 已进入主页」「✓ 关注 @xxx（翻了 N 篇 + 赞 a 评 b 后关注）」，然后**回到通知页**继续下一条，全部处理完才回首页 |

## 4. 纪律（别违反）

1. 默认 dry-run；写操作必须显式 `--yes`。
2. 正式号（prod）上任何写操作前，先确认账号闸门通过。
3. 一次只允许一个任务驱动浏览器（UI 已有互斥锁）。
4. 每日上限在 `xauto/data/limits.json`，超了自动停手，别绕过。
5. 出问题先看 `xauto/data/*.log` 与 `xauto/data/shots/` 截图，再动手改代码。

## 5. Git 推送（本机特有故障，别当成代码问题）
| 项 | 内容 |
|---|---|
| 现象 | `git push` 报 `Recv failure: Connection was reset` / `RPC failed; curl 52 Empty reply from server` / `Failed to connect to github.com:443`，且**同一条命令一会儿成功一会儿失败** |
| 根因 | 本机 `github.com:443` 链路抖动（代理客户端在切节点）。与仓库、凭据、代码都无关 |
| 判据 | `curl -s -o NUL -w "%{http_code}" https://api.github.com` 稳定返回 200，而 `https://github.com` 返回 000 → 就是链路抖动，不是断网 |
| 处理 | **逐提交推送 + 每次用 API 校验**（payload 小、断一次只损失一小段）：<br>`git -c http.version=HTTP/1.1 push origin <sha>:refs/heads/main`，每试一次后查 `api.github.com/repos/Aron0525/x-auto/git/ref/heads/main`，sha 对上了再推下一个 |
| 自检 | 远端真实 head 只能信 API：`curl -s https://api.github.com/repos/Aron0525/x-auto/git/ref/heads/main`。`git ls-remote` 走的是同一条坏链路，会跟着一起骗你 |
| 陷阱 | 抖动期间 git 可能输出 `Everything up-to-date` **但实际没推上去**（它连上了又断了，状态是假的）。所以「推了没」必须用 API 的 sha 和 `git rev-parse main` 比对，别信 push 的 stdout |
| 凭据 | 走 Windows 凭据管理器（`cmdkey /list` 有 `git:https://github.com`），无需另配 token；`gh` CLI 未安装 |
| 验证记录 | 2026-11-17：`febaee0`/`66e5347`/`a76ae08` 三个提交，逐提交重试约 15 次后全部推上，远端 head 与本地一致 |
